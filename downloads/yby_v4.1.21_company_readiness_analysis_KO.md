## 회사 업무용 적합성·완성도 분석자료

YBY V4.1.21 · 2026년 10월 20일 · 한국시간


> 종합 판단: 통제 조건을 충족한 사내 카드관리 보조업무의 시범 운영에 적합한 기반을 갖췄습니다. 전사 정식 운영의 승인이나 모든 결함이 없는 완제품이라는 판정은 아직 할 수 없습니다.


V4.1.20 대비 정책·지점 관리, 자기승인 통제, 하이패스 실물 확인, 암호화 백업·시험복원과 화면 모듈 분리가 추가되었습니다. 단순한 화면 시제품보다 구현 깊이가 높지만 회사 운영환경과 업무 목적의 검증은 남아 있습니다.

카드 보조업무·사용내역·통계의 구체적 경계 사례는 첫 번째 「카드관리 보조업무·사용내역·통계 분석자료」에 별도로 정리했습니다. 두 분석자료는 같은 배포본·증거를 사용합니다. 프로그램 수정판은 포함하지 않습니다.

## 05. 카드·정산 업무의 강점과 주의점

원본 보존과 실제 업무 맞춤


### 확인한 강점


- 서버에서 카드 상태·지점·금액·명세 합계·날짜·정산 상태를 검사합니다. 브라우저 입력만 믿지 않습니다.
- requestId 영수증과 revision 충돌 검출로 동일 요청 재시도·다중 담당자 수정에 대비합니다.
- 정산 실패 시 반납·출처 연결을 함께 되돌려 고아 이력 생성을 막습니다.
- 승인취소·정정·재보고는 원본과 연결을 보존하고, 완료 자료의 일반 저장 우회를 제한합니다.


### 현재 회사 업무와의 차이


별도 시스템 정산을 최종 기준으로 삼는 회사에서는 반납에 YBY 정산 입력이 요구되고 승인대기가 추가되는 점이 가장 큰 적합성 문제입니다. 정산 권한을 빼면 사용 반납도 막힙니다. 실물 회수 사실과 금융·정산 상태를 독립 관리하는 것이 우선입니다.


법인카드 상태 열거는 available/rented 중심입니다. YBY의 사용가능을 카드사 승인가능·분실정지 해제·한도 여유로 해석할 수 없습니다. 분실은 카드사 신고와 별도 사고 대장으로 즉시 처리하고, 프로그램에도 재불출 차단 상태를 추가하는 것이 좋습니다.


최고관리자 자기승인은 정책으로 금지할 수 있고, 허용 시 기본 사유·재인증을 요구합니다. 회사의 정식 외부 결재는 그 규정에 따라 유지하고 YBY의 자기승인 기록을 독립 사후 검토해야 합니다.


## 06. 사용내역·통계·현황의 완성도

데이터의 정의와 수록 범위에 따른 조건부 신뢰


| 항목 | 현재 평가 | 개선 방향 |

| 사용내역·출처 | 대장 연결·이관/승인·정정 보호 강점 | 외부 원본 문서/거래/개정키·공식 상태·최종수신 확인 |
| 통계 전체·개인·지점·부서·목적 | 같은 모델로 차원별 비교·Excel 제공 | 출처별·공식상태별 분리와 코드 정규화 |
| 월별 사용금액 | 문서 date 월에 전액 귀속 | 명세 실제 거래일 기준 별도 통계 |

| 업무 점검 | 결측/원본변경/자기결재와 점검 기록 | 월별 실적과 현재 미결의 기준시점 표시, 자동 대사 아님 |


합성 재현: 10/31 100원+11/1 200원 명세는 통계상10월300원·11월0원입니다. Excel합계225,000원 1행은 사용1회로 집계됩니다. 수기·외부 자료가 다른ID로 같은 거래를 나타내면 ID중복 제거로는 막지 못합니다. 이는 정의/수록 범위의 문제로 실제 회사 피해나 실적 오류를 단정한 것은 아닙니다.


정상적인 승인/이관 자료에 대해 비교·관리하는 기능은 갖췄습니다. 그러나 전사 확정금액·실제 거래월·사용빈도의 공식 보고로 쓰려면 외부 전수 대사와 집계 정의 확정이 필요합니다.


## 07. 보안·계정·최소권한 평가

보조업무에서도 카드번호·사용자·행선지·사용목적·금액은 회사가 보관범위와 접근자를 정해야 할 정보입니다. 실제 규정·법령 준수 인증은 본 기술 검토의 범위가 아닙니다.

## 11. 유지보수·검사·기술부채

큰 HTML을 줄인 다음에 필요한 일


### 좋아진 부분


HTML을802줄로 줄이고 CSS와 핵심 JavaScript6개로 분리했습니다. 기존 이력·매칭·통계·차량 모듈과 서버측 안정화 모듈을 유지하여 위험한 전면 재작성 없이 구조를 개선했습니다. 사용하지 않는 브라우저 XLSX 라이브러리도 제거했습니다.


### 남는 기술부채


- 핵심 JS는 전역 변수/함수 호환 방식입니다. 명확한 모듈 경계·공통 상태 관리·작은 컴포넌트로의 전환이 끝난 것은 아닙니다.
- CSP에 unsafe-inline이 남고 일부 이벤트는 HTML/문자열 생성과 결합됩니다. 이벤트 바인딩·렌더링 분리와 입력 처리의 지속 검토가 필요합니다.
- 서버는 전체 상태를 다루는 쓰기·전역 잠금이 남습니다. 트랜잭션과 영수증/원본 보호를 유지한 업무별 부분 변경이 후속 방향입니다.
- CI 정의는 ZIP에 있지만 실제 GitHub Actions Windows 성공을 확인하지 못했습니다. 설치 Python/Windows 조합별 검사를 자동화할 필요가 있습니다.


### 권장 개발 순서


현재397개 회귀검사를 유지 → 실물 반납/외부정산 경계 명세 → 역할/상태/출처 모델 정의 → 작은 업무API·집계모듈로 구현 → 실제회사자료 대사 → 회사Windows/복구 인수 → 적용 순서가 적절합니다. 분석 중 배포 코드를 수정하지는 않았습니다.
