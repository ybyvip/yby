# YBY V4.1.17 검증 결과

검증일: 2026-10-20 (한국시간). 기준 소스 V4.1.16, DB 스키마 8 유지.

## 실제 이전 첨부파일 검증

이전에 올린 **Book1.xlsx 원본**을 별도의 시험 서버에서 실제 HTTP API로 검사·업로드했습니다. 등록 카드는 **0장**으로 두어 사용자 화면의 차단 조건을 재현했습니다.

- 제목 5행 / 업무 6~9행을 읽어 **수신 가능 4행**을 확인했습니다.
- 실제 저장 결과 **신청서 4건 / 합계 정산서 1건(225,000원) / 정산 미수신 신청서 3건**을 확인했습니다.
- 은행명·끝자리·사용자·부서·지급일·예정일·반납일과 원본 참고 항목을 원문 값과 대조했습니다. 실제 개인정보는 로그/배포 문서에 출력하지 않았습니다.
- 신청서 4건과 정산서 1건의 실제 수신 확인 → 같은 원본 행의 1:1 매칭 → 카드 등록 대기 상태를 확인했습니다.
- 같은 파일 재검사에서 **중복 4건**, 자동 생성된 카드·업무 정산·반납·승인 **0건**을 확인했습니다.
- 실제 첨부 Excel과 회사 개인정보는 배포 ZIP·공개 화면 캡처에 넣지 않았습니다.

## 자동 검증

- Python 전체 서버 **305개 통과** (153.958초, 실패/스킵 없음). 이전 294개에 신규 11개를 추가했습니다. 기존 검사에서 ‘카드 미등록’을 오류로 간주하던 준비 자료는 새 수신 정책에 맞춰 조정했습니다. 실제 오류 행을 사용하는 부분 업로드 검사는 음수 금액으로 검증합니다.
- 최종 목적 구분 전달 및 원본 보완 표시 조정 후, 영향을 받는 신규 검사 **11개 재실행 통과** (5.526초). 반복 검사 건수는 합계에 더하지 않았습니다.
- Node 통계·이력 **24개 통과**, 실패/스킵 없음. 서로 다른 자동 검증 총 **329개**입니다.
- 신규 검사: 카드 0장에서도 신청·합계 정산 수신, 끝자리 중복 상태의 미확정 수신, 원본 은행/날짜/금액/부서/대체값 보존, 카드 등록 후 같은 원본 재업로드 중복 제외, V4.1.16의 전체 카드번호 포함 중복 해시 호환, 명시적으로 잘못 선택한 카드 차단을 확인했습니다.
- 매칭의 카드 등록 대기 → 실제 등록 후 불출 대기 → 정확한 불출 회차 연결, 목적을 그대로 전달했을 때 원본 보완 표시가 잘못 붙지 않는지, 빈 금액/0원 정산 미생성, 타 지점 수신 차단, 끝자리로 카드번호 미생성, 저장 실패 시 수신·원문·업무 원자적 롤백을 확인했습니다.
- 원본 ‘전표/정리/처리확인/불출/관리’의 완료 문구는 참고 항목으로 보존하며 YBY 승인 상태로 변경되지 않는지 확인했습니다.

## 실제 Chromium 검증

실제 첨부와 같은 제목 5행/자료 6~9행 구조의 **개인정보 없는 시험 XLSX**를 사용했습니다.

1. 카드 0장 → 4행 모두 선택 가능한 수신 가능 → 신청서 4건/정산서 1건/카드 연결 대기 4행 표시 → 업로드를 실행했습니다. 금액 없는 3행의 정산서가 생성되지 않고 월 한도/월 사용금액은 개별 정산에 포함되지 않습니다.
2. 신청서 전체 수신·정산서 전체 수신 → 정산서가 한 건뿐이어도 0/1 선택 상태 유지 → 같은 원본의 신청서/정산서를 각각 선택 → 매칭 저장 → ‘카드 등록 후 불출’ 및 등록 안내를 확인했습니다.
3. 등록 안내에서 실제 법인카드 등록 화면으로 이동 → 전체 카드번호를 직접 등록 → 매칭 목록의 불출 준비 → 해당 실제 카드 1장으로 불출 → 반납/정산 → 합계 225,000원 명세 1건의 YBY 승인대기 생성을 확인했습니다. 원본에 완료 문구가 있어도 자동 승인하지 않습니다.
4. 최종 실행에서 원본 ‘출장’이 목적 체크 항목으로, ‘현장 업무 3’이 상세목적으로 전달되는지 확인했습니다. 사용자가 값을 바꾸지 않았는데 ‘YBY에서 보완’으로 잘못 표시되지 않도록 확인했습니다.
5. 카드 등록·업무 처리 후 동일 파일을 재검사해 중복 4건/추가 업로드 비활성을 확인했습니다.
6. 원본 은행명·날짜·참고 상태의 문서 표시, 1920/1440/1024/768/390/320px에서 페이지 가로 넘침 없음, JavaScript 오류 없음을 확인했습니다. 실제 화면 캡처도 시각 확인했습니다.

## 기존 기능·업데이트

- V4.1.16 브라우저 회귀: 행별 지점·카드 선택, 중복/수신/매칭, 정확한 카드 불출 및 합계 반납 정산, 법인카드 제목 14칸/값 14칸 일치, 검색·실제 XLSX·PDF·지점 권한·모바일 통과.
- V4.1.15 브라우저 회귀: 잘못된 매칭의 처리 전 비밀번호 정정·이력, 처리 후 잠금, 정확한 불출 회차, YBY 별도 승인, 전체 통계 합계/범위/실제 XLSX·PDF·상태 색상 통과.
- 기본 브라우저: 보고서 작성·결재, 저장 오류 시 입력 보존, 실제 엑셀 및 전체 백업 ZIP, 하이패스·민원·공지·메모·메신저 저장, 모바일·키보드 동작 통과.
- **실제 V4.1.16 → V4.1.17 설치·기동·로그인**: 프로그램 교체 직후 DB 바이트 동일, 기존 불출/반납·정산·계정·보고서·첨부·하이패스/유류대·과거 스냅샷·외부 원문·적용 연결·매칭·수신 확인을 보존했습니다.
- 이전 V4.1.16 프로그램으로 실제 Excel 수신 자료를 만든 후 업데이트해, 원문·수신 확인·가져오기 기록의 DB 행 값이 그대로이고 V4.1.17 재업로드에서 중복 1건으로 분류되는지 확인했습니다. 기존 스키마 8을 유지합니다.
- 업데이트 전 실제 전체 백업 ZIP에 스키마 8 및 기존 자료가 담기는지 확인했습니다. 인증서/개인키·LAN 설정 보존은 시험 파일 바이트 비교이며 회사 인증서 실행 검사가 아닙니다.
- 읽기 전용 한글 원본 → 쓰기 가능한 사용자 실행 폴더 설치/기동/로그인/업무 저장, 중복 실행 같은 PID 및 원본 DB·재설치 자료 유지 검증을 통과했습니다.

## 배포와 한계

배포 파일 목록에 지정된 소스만 넣어 운영 DB·개인키·로그·실제 회사 Excel을 제외합니다. 최종 ZIP CRC·파일별 SHA-256·추출본 시작 무결성, Python 3.11 구문, JavaScript/인라인 구문, PowerShell BOM 및 이전 버전과 바이트 동일을 검사합니다. 게시한 실제 다운로드 URL에서 다시 받아 GET 200·ZIP CRC·내부 모든 파일 해시를 확인합니다.

회사 Windows/Edge/WebView2·실제 인증서 등록·방화벽 및 실제 Oracle 접속은 이 클라우드에서 실행하지 않았습니다. Oracle SQL/뷰·컬럼·권한 자료는 대기 중입니다. 실제 회사 PC에서 최종 실행 확인이 필요합니다. 고유번호 없는 별도 업무나 Oracle/Excel 교차 수집을 완전히 자동 판별하지 않으며 원본 식별 기준과 담당자 확인을 사용합니다.
