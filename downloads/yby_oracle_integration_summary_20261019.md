# YBY V4.1.6 이후 진행내역 및 Oracle 연동 상세 정리

작성 기준일: 2026년 10월 19일 · 한국 시간

문서판: 업무 기준 정리본 1.0

현재 단계: Oracle 자료 요청 완료 · 담당자 회신 대기

검토 기준: 배포된 YBY V4.1.6 소스, 사용자 설명과 확정 답변, 신청서·정산서 화면 및 PDF 원본

## 1. 현재까지의 결론과 작업 상태

목표는 외부 전자결재 프로그램의 Oracle DB에서 법인카드사용신청서와 법인카드사용정산서를 받아, 담당자의 확인을 거쳐 YBY의 불출·반납·사용정산에 활용하는 것이다. 기존 YBY 직접 작성 기능도 함께 제공한다.

외부 두 문서는 각각 독립적으로 작성된다. 신청서와 정산서 사이의 외부 연결번호를 요구하지 않는다. 각 문서 자체의 고유키는 중복 수신과 변경 관리를 위해 필요하다. 정산서와 YBY 불출 건의 연결은 담당자가 확인·확정하고 YBY 안에 저장한다.

외부 결재 상태는 참고 정보로 표시하고 YBY 결재는 별도로 진행한다. 외부 미결재·결재중 상태라는 이유로 YBY의 반납·정산 작성·기존 권한에 따른 최종결재를 막지 않는다.

| 구분 | 현재 상태 | 의미 |
|---|---|---|
| 기존 운영·검토 기준 | V4.1.6 배포본 | 현재 설계는 이 버전을 기준으로 함. 실제 회사 PC의 상태를 원격 확인한 것은 아님 |
| 외부 DB 종류 | Oracle로 확인 | 버전·접속 방식·스키마는 추가 확인 필요 |
| 업무 흐름·권한·분류 | 사용자 기준 확정 및 설계 정리 | 이 문서에 확정 내용을 통합함 |
| 문서 양식 분석 | 사진 및 PDF 원본 확인 | 화면 항목을 YBY 항목과 대응시킴 |
| Oracle 정보 요청 | 사용자가 담당자에게 요청 완료 | 현재 답변과 설명자료 도착을 기다리는 중 |
| 신규 연동 프로그램 | 구현·배포 전 | Oracle 접속·조회·동기화·연동 화면이 이미 구현된 상태는 아님 |
| 이번 산출물 | 상세 정리 문서 | PDF·Word·Markdown 및 관련 문서 묶음 |

V4.1.6 배포 검증 보고서에는 기존 자동검사 174개 통과 기록이 있다. 이는 당시 버전의 검사 기록이며 Oracle 연동 기능이 검증되었다는 뜻은 아니다. 이번 작업은 기존 자료를 재검토하고 설계를 정리한 문서 작업이다.

## 2. V4.1.6 이후 진행한 일

| 단계 | 진행 내용 | 현재 정리 |
|---|---|---|
| 연동 가능성 검토 | 기존 API·저장 방식·동기화 확인 | 기존 업무 처리에 외부 수신 단계를 추가하는 방향 |
| 외부 자료 범위 확정 | 사용신청서와 사용정산서 2종 | 외부 DB에서 읽어옴 |
| 업무 연결 구상 | 신청서는 불출 작성, 정산서는 반납·정산 작성 | 담당자가 원본을 확인하고 처리 |
| 결재 기준 확정 | 외부 결재와 YBY 결재 분리 | 외부 상태를 YBY 승인 결과로 자동 치환하지 않음 |
| 문서 관계 확인 | 두 문서가 독립 입력임을 확인 | 외부 상호 연결번호를 전제로 삼지 않음 |
| 카드 식별 기준 확정 | 지점 + 카드 끝 4자리 | 내부 카드 ID에 대응시키고 유일성 확인 |
| 지점 기준 확정 | 기안 소속의 지점명 활용, 팀·실만 있으면 본사 | 녹색물류팀은 본사로 확정 |
| PDF 원본 확인 | 신청서·정산서 각 1페이지 검토 | 금액·날짜·첨부 표시·하단 항목 보완 |
| DB 종류 확인 | Oracle 사용 확인 | 실제 구조·조회 방법은 대기 |
| 정보 요청 준비 | DB 담당자용 요청서 작성·사용자 전달 | 사용자가 요청 완료했다고 알려줌 |
| 현재 작업 | 기존 문서를 최신 합의로 통합 | 이 정리본을 기준으로 회신 후 작업을 이어감 |

초기 검토에서 확인 대상으로 남겼던 지점 분류와 문서 관계는 이후 사용자 답변으로 확정되었다. 본 정리본은 그 최신 답변을 적용한 기준이며, 과거 문서의 ‘확인 예정’ 문구와 혼동하지 않도록 한다.

## 3. 확정된 업무 기준

| 번호 | 확정 내용 | 반영 원칙 |
|---|---|---|
| C01 | 외부 원천은 Oracle DB | 회사 YBY 서버에서 필요한 자료를 조회 |
| C02 | 수신 대상은 신청서·정산서 | 문서 종류를 나누어 관리 |
| C03 | 두 문서는 독립 작성 | 외부 연결번호가 없어도 수신 가능 |
| C04 | 외부 결재는 참고, YBY 결재는 별도 | 외부 미결재여도 YBY 업무 진행 가능 |
| C05 | 최고관리자는 모든 지점 조회 | 조회·검색·상세·증빙에도 같은 범위 적용 |
| C06 | 지점 계정은 자기 지점 조회 | 서버에서 소속과 기존 기능 권한을 검사 |
| C07 | 지점명 있는 소속은 해당 지점 | 서울지점(총무팀) → 서울 / 총무팀 |
| C08 | 지점명 없이 팀·실이면 본사 | 녹색물류팀 → 본사 / 녹색물류팀 |
| C09 | 카드 표시는 지점 + 끝 4자리 | 본사-5545, 인천-5545로 구분 |
| C10 | 신청서 선택 후 불출 작성 | 실제 카드 지정과 불출 확정은 담당자가 수행 |
| C11 | 정산서는 반납·정산 작성에 활용 | 담당자가 해당 불출 건과 원본 정산서를 확인 |
| C12 | 직접 작성 경로 유지 | 외부 자료 없이도 기존 업무 가능 |

외부 신청자, 실제 카드 사용자, YBY 로그인 처리자는 서로 다를 수 있다. 원본 신청자와 실제 사용자를 확인하고, YBY에서 누가 처리했는지도 별도로 기록하는 설계로 정리했다.

## 4. 두 업무 흐름과 직접 작성 경로

### 4.1. 외부 사용신청서에서 불출하기

Oracle 신청서 조회 → 신청서 수신함 → 담당자 원본 확인·선택 → 불출 양식에 신청내용 채움 → 실제 카드·사용자·기간 확인 → 불출 확정 → 원본 신청서와 YBY 불출 건 연결 보존.

- 체크·선택은 작성 단계 진입이다. 실제 불출 확정 시점에 카드 상태를 변경한다.
- 사용목적·부서·반납예정일을 불러오되, 원본 요청일과 실제 불출일을 구분한다.
- 기안자가 여러 출장자 중 한 명이라고 해서 그 사람을 실제 카드 사용자로 자동 확정하지 않는다.
- 이미 불출 중이거나 만료된 카드 등은 기존 YBY 검증을 적용한다.
- 원본을 다시 수신하거나 여러 담당자가 동시에 선택해도 같은 처리를 중복 생성하지 않도록 한다.
- 문서 1건당 여러 카드/불출을 허용할지는 실제 문서 구조와 운영 기준 확인 후 결정한다.

### 4.2. 외부 사용정산서에서 반납·정산하기

Oracle 독립 정산서 조회 → 정산서 수신함 보관 → 담당자가 YBY 불출 건 선택 → 정산서 후보 조회 또는 직접 검색 → 문서·사용자·기간·카드 확인 → 연결 확정 → 외부 결재 상태와 명세 표시 → 반납·정산 내용 확인 → YBY 반납·정산 등록 → YBY 결재.

- 외부 미결재 문서도 수신·조회·활용할 수 있다.
- 카드·지점·사용자·기간 등으로 후보를 제시할 수 있으나 담당자 확인 전에 관계를 확정하지 않는다.
- 같은 카드의 과거 정산서가 늦게 들어오면 해당 과거 불출 건을 확인한다. 현재 사용 중인 다른 건에 임의 연결하지 않는다.
- ‘카드 실물 반납’, ‘외부 정산서 결재’, ‘YBY 정산·결재’는 서로 다른 상태로 보존한다.
- 반납과 정산 등록의 실제 저장은 기존 YBY 업무 검증 및 트랜잭션 절차와 연결한다.
- 외부 정산서가 아직 연결되지 않은 상태를 카드 미사용으로 처리하지 않는다.

### 4.3. YBY 직접 작성과 함께 사용하기

직접 불출 작성 → 직접 반납·정산 작성 → 기존 YBY 결재 흐름을 유지한다. 직접 작성한 불출에도 외부 정산서를 나중에 선택·연결할 수 있도록 설계한다.

이미 YBY에서 작성한 정산에 해당 외부 문서가 뒤늦게 수신되면, 기존 자료에 연결하는 처리가 필요하다. 새 정산을 무조건 추가하여 금액이 중복 집계되지 않도록 한다. 확정 후 연결 변경의 권한·사유·이력 세부 정책은 구현 단계에서 정한다.

## 5. 권한·지점·카드 분류 기준

### 5.1. 지점 분류 순서

기안자 정보에서 소속 구간을 확인하고, 명시적인 지점명 판별을 팀·실 분류보다 우선 적용한다. 본문에 등장한 출장지나 참조자 이름을 소속 지점으로 사용하지 않는다.

| 소속 예시 | YBY 지점 | 원본 부서 보존 |
|---|---|---|
| 서울지점(총무팀) | 서울 | 총무팀 |
| 인천지점(지원실) | 인천 | 지원실 |
| 광주지점(운영팀) | 광주 | 운영팀 |
| 정봉지점으로 명시된 소속 | 정봉 | 하위 부서가 있으면 별도 보존 |
| 녹색물류팀 | 본사 | 녹색물류팀 |
| 지점명 없이 팀·실로 기재된 소속 | 본사 | 원본 명칭 보존 |
| 소속 공란·판독 불가·여러 지점 충돌 | 확인 필요 | 최고관리자가 확인 |

DB에 구조화된 소속 필드가 있으면 그 필드와 화면 표기의 관계를 확인해 대응표를 만든다. 전체 기안자 문자열만 있으면 소속 부분을 분리한다. 사용자 설명으로 본사로 분류하기로 한 팀·실과, 소속 자체가 없는 경우는 구분한다.

현재 검토한 V4.1.6의 고정 지점 목록은 본사·서울·인천·정봉·임원실이다. 사용자 예시에 포함된 광주 등 실제 운영 지점은 구현 시 지점 목록·계정 권한·조회 범위를 함께 맞춰야 한다. 명시된 지점을 기존 목록에 없다는 이유로 본사로 바꾸지 않는다.

### 5.2. 카드 연결 기준

- 표시·조회 기준: 지점 + 카드 끝 4자리. 예: 본사-5545와 인천-5545.
- 내부 저장: 기존 YBY 카드 ID를 유지하고 원본 카드 표기와 대응 관계를 보존한다.
- 카드 끝자리 앞의 0을 보존한다. ‘0052’를 숫자 52로 취급하지 않는다.
- 같은 지점에 일치 카드가 1장인지 확인한다. 없으면 미등록/확인 필요, 여러 장이면 중복/선택 필요로 표시한다.
- 카드사가 제공되면 보조 검증에 활용한다. PDF 예시의 ‘신한.4518’은 원문과 카드사·끝자리를 함께 보존한다.
- 카드 식별과 불출 건 식별은 별개이다. 카드를 찾은 뒤 해당 사용기간·사용자를 확인한다.

### 5.3. 접근 권한

최고관리자는 모든 지점의 수신 자료를 조회한다. 지점 사용자는 자기 지점 자료만 조회하고, 실제 불출·정산 처리는 기존 기능 권한도 확인한다. 지점의 조회 권한이 YBY 최종결재 권한 확대를 뜻하지 않는다. 현재 정산 결재는 기존 최고관리자 권한 기준을 따른다.

목록뿐 아니라 검색 결과·건수·상세·증빙 다운로드·연결·처리 API에서도 서버가 같은 권한을 검사해야 한다.

## 6. 두 PDF 원본에서 확인한 내용

- 카드수령일·반납일과 사용일에는 10.15가 표시되어 있다. 사용일 항목 자체에 연도가 없어 DB 날짜 원본을 확인해야 한다.
- 양식은 15행이며 이번 예시에서 실제 입력된 거래는 2건이다.

| 명세 | 원본 구분 | 내역 | 금액 | 원본 인원 정보 |
|---|---|---|---:|---|
| 1 | 업협 | 음료대 | 6,000원 | 총 4명 표시 |
| 2 | 업협 | 중식대 | 60,000원 | 총 4명 표시 |
| 합계 | | | 66,000원 | 인원수와 금액 계산은 분리 |

2건의 합계는 문서 합계와 일치한다. 인원이 4명이라고 해서 각 거래금액에 4를 다시 곱하지 않는다. 원본에 실제 수량·단가가 없으면 거래금액 중심으로 수신한다. 내부적으로 1건 × 거래금액으로 표현하더라도 실제 이용 인원이 1이라는 뜻은 아니다.

빈 행은 거래로 수신하지 않는다. 이 예시의 15행을 모든 외부 문서의 최대 명세 수로 가정하지 않는다. ‘업협’은 YBY 업무협의 구분과 대응시키되 원본 값도 보존한다.

### 6.3. 결재·증빙 확인 범위

두 PDF에는 ‘결재일’과 서명이 표시되어 있다. 미결재·결재중·완료·반려·취소 상태는 실제 DB 코드와 이력으로 연결해야 한다. 참조확인 체크, 결재마감일, 서명 이미지, 실제 결재 완료시각은 서로 구분한다.

정산서에는 ‘첨부파일 - 영수증.jpg’ 표시가 있으나 페이지에 실제 영수증 이미지는 보이지 않는다. PDF의 내장 첨부파일 목록도 0개로 확인했다. 원본 영수증 파일의 내용은 확인하지 못했다.

연동 시 첨부 메타데이터와 실제 파일을 별도로 읽을 수 있어야 한다. 정산서 PDF 자체와 영수증 파일을 구분하고, ‘첨부 이름만 수신’과 ‘실제 파일 수신 완료’를 나누어 표시한다.

## 7. 외부 항목과 YBY의 대응

아래는 논리적 대응이다. 실제 Oracle 컬럼명이나 조회 SQL이 확정된 표는 아니다.

| 원본 항목 | YBY 반영 위치 | 처리 원칙 |
|---|---|---|
| 문서 내부 ID·문서번호 | 외부 문서 식별·수신 이력 | 종류별 독립 관리, 중복 방지 |
| 기안 소속 | 지점·부서 | 확정된 지점/팀·실 기준 적용 |
| 기안자·사번 | 원본 신청/작성자 | 실제 사용자·YBY 처리자와 구분 |
| 제목 | 수신 목록·원본 상세 | 원본 유지 |
| 사용요청일 | 예정 사용일 | 실제 불출일과 구분 |
| 반납예정일 | 불출 작성 예정일 | 담당자가 확인 |
| 사용목적·세부목적 | 불출/정산 목적 | 구분과 서술을 보존 |
| 카드사·끝자리 | 카드 후보 조회 | 지점 결합 후 내부 ID 연결 |
| 카드수령일·반납일 | 연결 검토용 원본 날짜 | 실물 인수·회수 확인과 구분 |
| 명세행 고유키·순번 | 원본 명세 추적 | 재수신·정정 시 식별 |
| 건별 사용일·사용처 | 건별 정산 명세 | 날짜 연도·문자열 확인 |
| 건별 금액·합계 | 거래금액·정산 총액 | 금액 단위·합계 대조 |
| 사용인원·세부내역 | 참여자·상세내역 | 인원과 금액 계산 분리 |
| 특기사항 | 원본 메모·작성 참고 | 수정 시 원본과 보완값 구분 |
| 외부 결재 상태·이력 | 외부 상태 표시 | YBY 결재와 독립 |
| 수정시각·차수 | 동기화·변경 감지 | 구버전으로 덮어쓰지 않음 |
| 첨부 정보 | 실제 증빙 수신·연결 | 파일명과 파일 수신을 구분 |

## 8. 화면 구성안과 상태 표시

이 절은 구현을 위한 구성안이다. 실제 화면과 저장 필드는 Oracle 구조를 확인한 뒤 개발한다.

### 8.1. 외부자료 수신함

신청서/정산서 탭을 두고, 문서번호·제목·지점·부서·작성자·사용일·외부 결재 상태·수신시각·연결 여부를 표시한다. 원본 상세, 불출 작성, 반납·정산 연결, 기존 YBY 건 보기 동작을 제공하는 방향이다.

### 8.2. 기존 불출·반납 화면 보완

불출 작성에는 ‘외부 신청서에서 작성 / 직접 작성’을 제공한다. 반납회수 행에는 카드·사용자·예정일과 함께 정산서 수신/연결 여부, 외부 결재 상태, YBY 정산 상태와 상세/연결 동작을 표시한다.

반납 양식에서는 외부 명세를 불러오거나 직접 작성한다. 입력 중 원본 상태가 갱신되어도 담당자의 입력을 덮어쓰지 않도록 해야 한다.

### 8.3. 서로 구분할 상태

| 관리 대상 | 표시 예시 | 의미 |
|---|---|---|
| 원본 수신 | 수신/재수신/확인 필요/실패 | Oracle에서 자료를 받았는가 |
| 문서 연결 | 미연결/후보 있음/연결 완료 | YBY의 어느 건에 사용했는가 |
| 외부 결재 | 미결재/결재중/완료/반려/취소 등 | 실제 DB 코드 확인 후 대응 |
| 카드 실물 | 불출 중/반납 확인 | 실제 카드 업무 상태 |
| YBY 정산 | 승인대기/승인완료/반려됨/재보고대기/승인취소 | 기존 YBY 처리 상태 |
| 증빙 수신 | 이름만 수신/파일 수신/확인 필요 | 실제 파일을 확보했는가 |

외부 결재 상태값은 예시 명칭이다. 실제 시스템의 코드와 의미를 받은 뒤 대응한다. 미수신은 미연결·미사용과 다르며, 외부 승인완료가 YBY 자동승인을 뜻하지 않는다.

## 9. Oracle 수신·연결·변경 처리 설계 방향

### 9.1. 기본 구성

Oracle 읽기 전용 조회 → 문서별 수신·검증 → 지점 분류 및 카드 후보 확인 → YBY 수신함 보관 → 담당자 연결·작성 → 기존 YBY 업무 처리·변경 감지 → 화면 반영.

조회는 각 접속 PC가 아닌 회사 YBY 서버에서 수행하는 방향이다. 외부 DB의 문서 등록·수정·삭제·결재 권한은 요청하지 않는다. Oracle 버전과 접속 조건을 확인하여 Python 접속 드라이버·Thin 모드·별도 Oracle Client 필요 여부를 정한다.

### 9.2. 수신 및 연결 기록

외부 시스템·문서 종류·문서 내부 고유키로 원본을 구분한다. 문서 표시번호, 수정차수/시각, 원본 값과 수신 이력, 분류·연결 결과를 보존한다.

외부 신청서↔YBY 불출, 외부 정산서↔YBY 불출/정산을 각각 관리한다. 두 외부 문서 사이의 관계를 임의 생성하지 않는다. 외부 수신 기록은 기존 업무 저장으로 지워지지 않도록 별도 보관 구조를 설계한다.

### 9.3. 재수신·충돌·원본 변경

- 동일 원본의 반복 수신으로 불출·정산·금액을 중복 생성하지 않는다.
- 늦게 도착한 구버전 자료가 최신 자료를 덮어쓰지 않도록 변경시각·차수 등을 검증한다.
- 외부 상태 변경은 외부 표시와 변경 이력에 반영하고 YBY의 확정 결재는 자동 변경하지 않는다.
- 승인완료 정산의 원본 금액·명세가 바뀌면 차이와 확인 필요 상태를 표시하고 기존 정정·재보고 절차와 연결한다.
- 잘못된 문서 연결 변경, 여러 정산서·부분 정산, 거래 취소/환불의 세부 정책은 실제 사례 확인 후 결정한다.

### 9.4. 주기·오류·화면 반영

현재 YBY 화면은 약 2초마다 서버 변경을 확인한다. 이 값은 Oracle 조회 주기가 아니다. 실제 반영 시간은 Oracle 조회 주기, 처리 시간, 네트워크, 화면 갱신의 영향을 받는다.

Oracle 증분 조회 기준과 허용 부하를 받은 뒤 조회 주기·초기 수신 범위·재처리를 정한다. 확인 전 특정 실시간 속도를 보장하지 않는다. 연결 장애 시 기존 YBY 업무를 유지하고 마지막 성공 시각과 수신 상태를 보여주는 방향으로 설계한다.

## 10. 담당자에게 요청한 내용과 회신 대기표

사용자는 Oracle DB 담당자에게 정보 요청을 완료했다고 알려주었다. 실제 테이블·SQL·설명자료의 회신은 아직 수신하지 않았다. 현재 단계에서 같은 자료를 다시 요청할 필요는 없다.

| 대기 항목 | 필요한 이유 | 회신 시 확인할 내용 |
|---|---|---|
| Oracle 버전·접속 방식 | 드라이버·접속 구성 선택 | Service Name/SID, TNS·Wallet 등 |
| 스키마·테이블/뷰·조회 SQL | 실제 수신 쿼리 작성 | 신청서·정산서·결재·명세 위치 |
| 양식 구분·고유키 | 문서 선택 및 중복 방지 | 양식 ID, 내부 문서 ID, 명세행 ID |
| 본문 저장 구조 | 필드 추출 방식 결정 | 컬럼/테이블 또는 CLOB·HTML·XML·JSON |
| 상태코드·결재 이력 | 정확한 외부 상태 표시 | 코드 의미·결재시각·반려/취소 |
| 수정·삭제 정보 | 증분 수신·변경 대조 | 수정시각·차수·삭제/취소 표시 |
| 직원·소속·카드 필드 | 분류·후보 조회 | 원문 구조·코드·끝자리 저장 방식 |
| 날짜·금액 자료형 | 잘못된 계산·날짜 방지 | 연도·시간대·통화·환불 표기 |
| 첨부 저장·조회 방법 | 실제 영수증 수신 | 메타데이터·파일/저장소 접근 |
| 조회 규모·샘플·시험 조건 | 부하·오류·예외 검증 | 문서 수, 명세 수, 허용 주기 |

실제 접속 비밀번호는 정리 문서나 채팅에 기록하지 않고 설치 시 별도로 설정한다. 이번 문서 묶음에는 접속 비밀정보가 들어 있지 않다.

### 10.1. 추가 운영 결정이 필요한 사항

- 최초 가져올 과거 자료의 기간과 조회 주기.
- 문서 한 건과 카드/불출/정산의 다건 관계, 분할 정산 처리.
- 원본 변경·연결 해제·담당자 보완의 허용 범위와 이력.
- 외부 수령/반납 기재일과 YBY 실제 처리일의 표시 방식.
- 누락·다중 매칭·합계 불일치·첨부 미수신 자료의 담당자 조치 방식.
- 실제 운영 지점 전체 목록과 기존 계정의 권한 대응.

위 항목은 예외 처리 정책을 정하기 위한 대기 사항이다. 이미 확정한 독립 문서·별도 YBY 결재·팀/실 본사 분류 기준을 다시 미정으로 돌리는 것은 아니다.
