### 정식 업무 적용 전에 우선 해결할 다섯 가지


- 사용자 비밀번호를 최고관리자에게 보여주는 기능을 회사 보안 정책에 맞게 재검토합니다. 권장 방식은 본인만 아는 비밀번호와 관리자 초기화입니다.
- 백업을 암호화된 별도 저장소에 보관하고 보존·삭제·용량 경보를 정합니다. 현재 ZIP은 암호화되지 않습니다.
- 새 Windows PC로 DB·첨부·계정·인증서 신뢰까지 복구하는 시험을 완료합니다. 전체백업 ZIP만으로 동일 접속 환경까지 복원되지는 않습니다.
- 관리자 자기 결재, 관리자 암호 초기화 후 기존 세션 유지, ALL 범위 계정의 전권을 회사가 명시적으로 승인하거나 제한합니다.
- 실제 회사 Windows/Edge/WebView2·보안 프로그램·사내망에서 담당자와 사용자 인수 시험을 수행합니다.


> 권고: 기존 업무 장부와 병행하여 시작하고, 금액·건수·반납·결재 상태를 대조한 뒤 확대하십시오. 자동 검사 364개 통과만으로 전사 운영 승인을 대신할 수는 없습니다.


## 02. 분석 범위와 증거의 신뢰도

실제 확인 · 기존 기록 · 미확인을 분리


### 직접 수행한 범위


- 지정 GitHub 주소에서 ZIP을 다시 내려받아 SHA-256과 ZIP CRC를 확인했습니다. MANIFEST에 기록된 247개 파일의 해시가 모두 일치했습니다.
- 그 ZIP을 별도 폴더에 풀어 서버·DB·권한·인증서·백업·이관·화면 코드를 검토했습니다. 실제 회사 DB나 회사 서버에 접속하지 않았습니다.
- 추출본에서 Python 전체 검사 332개와 Node 검사 32개를 재실행했습니다. 최신 Chromium 화면 시나리오도 다시 실행했습니다.
- 합성 자료로 계정 목록 노출, 재인증 시도 제한, API 카드번호 반환, ALL 범위 권한, ZIP 백업 보호 범위를 관찰했습니다.
- 5,000개 이력·동시 클라이언트 10개·60회 조회의 짧은 로컬 부하 검사를 수행했습니다.


### 기존 배포 기록으로만 확인한 범위


V4.1.19→V4.1.20 설치·자료 보존, 한글 경로·읽기 전용 원본에서의 실행 폴더 준비, 과거 브라우저 회귀, 원본 Book1.xlsx 대응 결과는 기존 배포 검증 자료를 참조했습니다. 이번 보고서에서는 이 항목을 모두 새로 실행했다고 주장하지 않습니다.


### 직접 확인하지 못한 범위


회사 실제 Windows와 인증서 저장소, 도메인 정책·방화벽·VPN, 회사 운영 DB 전체, 실제 Oracle 연결, 다일간 연속 운영, 전원 차단·디스크 고장, 대규모 쓰기 경합, 제3자 침투 시험은 미확인입니다. CI 설정 파일은 있으나 GitHub Actions의 실제 성공 이력까지 검증한 것은 아닙니다.

## 03. 프로그램의 방향과 구조

단일 서버를 기준으로 지점별 업무를 통합하는 경량 시스템


YBY의 방향은 흩어진 카드 불출·반납·사용정산·문서 결재와 하이패스·유류대카드 배부를 한 서버에서 관리하는 것입니다. Excel 과거 자료를 보존해 이관하고, 향후 Oracle 문서를 받아 수동 확인 후 연결하는 방향은 현업 관리 도구로 적절합니다.


> Windows 실행 → 사용자 전용 실행 폴더 → Python HTTPS 서버 → 서버 측 검증·트랜잭션 → SQLite DB / 첨부 저장 → 지점별 화면·통계·내보내기


| 계층 | 확인한 구현 | 평가 |
| --- | --- | --- |
| 실행·설치 | RUN_LAN_WINDOWS.bat, windows_bootstrap.py, run_ready.py | 사용자 경로·패키지 해시·중복 실행·기존 DB 보존 고려 |
| 통신·로그인 | 사설 CA 기반 HTTPS, Windows 로그인 창, 서버 세션 | 사내망 사용에 맞는 구조. PC별 신뢰 등록·서버 가동 필요 |
| 업무 처리 | operations.py + domain.py + 업무 모듈 | 전용 API로 불출·반납·승인·정정 검증 |
| 보관 | SQLite 레코드별 JSON, 외부 수신·매칭·중복 등록 테이블 | 기능 확장은 쉽지만 조회·쓰기는 전체 상태 처리 비중이 큼 |

### 구조적으로 잘된 점


브라우저 자료만 믿지 않고 서버가 권한·금액·날짜를 검사합니다. requestId 영수증으로 재전송 중복을 막고 revision으로 동시 수정 충돌을 검출합니다. 일반 저장 경로로 완료 이력을 마음대로 덮어쓰지 못하게 제한하며, 이관 수기 정정은 별도 API와 사유·비밀번호 확인을 사용합니다. [E03~E06]


### 구조적 한계


단일 PC·단일 프로세스·SQLite와 사용자 로그인 계정에 운영이 집중됩니다. 이 구조 자체가 업무용 사용 불가를 뜻하지는 않습니다. 다만 고가용성, 장기 대용량, 직무 분리, 운영 자동화까지 확보한 전사 플랫폼과는 수준이 다릅니다.

## 05. 법인카드·정산 업무의 강점과 주의점

자료 등록과 실제 승인·회계 확정을 구별


### 잘된 점


- 신청자와 실제 카드 사용자를 구분하고 신청일·반납예정일·실제 불출/반납 이력을 남깁니다. 카드 상태를 일반 화면 저장으로 임의 전환하지 못하도록 서버가 제한합니다.
- 정산 건별 명세는 1~100건, 수량×단가와 합계를 서버에서 검증합니다. 원화 정수 금액을 쓰므로 일반적인 소수점 부동 오차를 피합니다.
- 승인 취소는 원 승인 내역을 보존하고 사유·새 재보고 대기 건을 생성하는 방식입니다. 단순한 마이너스 승인 행만 추가하는 구조보다 추적이 쉽습니다.
- 불출 완료와 반납·정산 상태를 구별하고, 이관 완료 자료는 YBY 승인완료로 임의 변경하지 않습니다. [E04~E07]


### 보완할 점


현재의 “정산”은 카드 사용 설명과 결재·대장을 관리하는 업무 개념입니다. 카드사 청구 명세 대사, 회계 전표 확정·마감, 부가세/환율 처리, ERP 전송·취소 통제까지 확인한 것은 아닙니다. 이 기능이 필요한 회사에서는 별도 명세와 회계 승인 절차가 필요합니다.


| 주의 항목 | 업무 영향 | 권고 |
| --- | --- | --- |
| 해외겸용 카드 표시 | 카드 속성 표시와 외화 정산 지원은 서로 다름 | 원화 환산액·환율·통화가 필요한지 별도 확정 |
| 관리자 자기 승인 | 기능 요구에는 부합하나 직무 분리가 약해짐 | 예외 승인 사유와 사후 독립 점검, 금액별 정책 |

### 과장해서는 안 되는 부분


로그인 보안과 비밀번호 열람 저장소는 별개입니다. 검증용 해시가 강해도, 현재 비밀번호를 복원할 수 있게 보관하는 기능이 있으면 관리자·서버·백업 유출의 피해 범위는 커집니다. HTTPS 역시 서버 디스크·내보낸 파일·다운로드한 백업을 암호화하지 않습니다.


MFA·회사 SSO, 중앙 보안 감시, 침해 대응 자동화, 인증서 배포의 회사 정책 적합성은 확보되었다고 볼 수 없습니다. 아래의 개선 항목은 보안 장치가 전혀 없다는 뜻이 아니라 기업 운영 기준에 맞춘 추가 통제 요구입니다.


## 10. 우선 보완 F01 — 비밀번호와 재인증

높음 · 정책상 위험 + 재현한 통제 공백


### 확인 사실


로그인 비밀번호는 검증용 해시 외에 복원 가능한 암호문으로도 저장됩니다. Windows는 해당 Windows 사용자 DPAPI, 비Windows는 Fernet를 씁니다. ALL 범위 계정은 본인 비밀번호로 재인증한 후 다른 사용자의 현재 비밀번호를 API로 받아볼 수 있습니다. 조회 이력이 남고 화면은 30초 후 숨깁니다. 이는 이전 기능 요구를 반영한 구현입니다. [E15]


### 업무·보안 영향


최고관리자나 서버 실행 계정이 침해되면 다른 사용자 비밀번호와 행위의 신뢰도까지 영향을 받을 수 있습니다. 같은 비밀번호를 다른 회사 서비스에 재사용했다면 피해가 확대됩니다. 30초 표시 제한은 이미 열람·복사된 비밀번호를 회수하는 장치가 아닙니다. 사용자의 현재 비밀번호를 알아야 계정 관리가 가능한 것은 아닙니다.


### 추가 확인: 재인증 실패 제한이 공통으로 적용되지 않음


로그인과 비밀번호 열람에는 제한이 있지만 /api/verify-current-password는 별도 실패 횟수 제한 없이 해시 검증을 수행합니다. 이미 로그인한 합성 계정으로 틀린 비밀번호를 6회 연속 전송하면 모두 403이며 제한 응답은 없었습니다. 단 6회로 대규모 공격 성공을 입증한 것은 아니지만, 이 경로에 공통 제한 코드가 없는 점은 확인했습니다. [E01 app.py:880]


### 권고 수정


- 정식 업무용 기본값은 비밀번호 표시·복원 저장을 사용하지 않고, 관리자 초기화→사용자 변경 방식으로 전환합니다. 기존 저장 암호문·키는 정책에 따라 정리합니다.
- 모든 재인증 경로에 계정·세션·IP별 제한, 잠시 대기, 감사 기록을 공통 적용합니다. 관리자에게는 MFA/SSO를 중장기 검토합니다.
- 관리자 암호 초기화 후 기존 세션을 보존하는 현재 동작은 편의성 요구입니다. 침해 대응 시에는 세션 강제 종료를 함께 실행하도록 절차화하고 자동 종료 옵션을 둡니다.


### 완료 기준


일반 로그인·기존 해시 검증은 유지되고 타인 비밀번호 조회는 불가해야 합니다. 재인증 반복 실패에 지연/429가 적용되고 정상 사용자가 복구할 수 있어야 합니다. 계정 침해 시 기존 세션 종료까지 확인하십시오. 비밀번호 열람을 유지한다면 회사 책임자의 위험 수용과 별도 예외 통제가 필요합니다.


## 11. 우선 보완 F02 — 디스크·백업·민감 정보

높음 · 직접 재현한 보호 범위의 한계


### 확인 사실


DB는 일반 SQLite이며 업무 데이터와 카드번호를 담습니다. 최신 보조 스냅샷은 JSON입니다. 전체백업 ZIP은 체크섬 검증은 하지만 암호화하지 않습니다. 비Windows에서는 비밀번호 보관용 Fernet 키도 같은 ZIP에 포함됩니다. 합성 자료 시험에서 ZIP만으로 DB를 읽고 그 키로 저장 비밀번호를 복호화할 수 있음을 확인했습니다. 비밀번호 값 자체는 공개 시험 결과에 기록하지 않았습니다. [E05, E15]


> Windows DPAPI와 Linux Fernet를 구별해야 합니다. Windows 백업 ZIP 하나만으로 비밀번호까지 해독된다고 결론 낸 것은 아닙니다. 다만 두 환경 모두 업무 DB·첨부를 담은 ZIP 자체는 암호화되지 않습니다.


### 카드번호 표시와 API의 차이


일부 대장 화면은 카드 끝자리로 가리지만, 해당 지점 카드 열람 권한이 있는 계정의 /api/state에는 전체 카드번호가 전달됩니다. 이는 무권한 지점 침범이 아니라, “화면에서 가렸으니 전체 번호가 클라이언트에 없다”고 이해하면 안 된다는 의미입니다. 카드 전체번호가 필요한 역할과 내보내기 범위를 정해야 합니다. [E01 app.py:360, E13]


### 권고


- 서버 디스크 암호화와 Windows 파일 ACL을 IT 담당자가 확인합니다. POSIX chmod만으로 Windows 세밀한 ACL 보호를 입증할 수 없습니다. 인증서 폴더는 별도 icacls 규칙이 구현되어 있습니다.
- 백업을 암호화된 별도 저장소로 전송하고, 복호 키는 백업과 분리해 관리합니다. 다운로드 폴더·USB·개인 클라우드에 평문 ZIP이 남지 않게 합니다.
- DB·스냅샷·첨부·내보낸 XLSX/PDF·로그에 대한 보존 기간, 접근자, 폐기 절차를 정합니다. 개인정보와 카드 정보는 실제 필요한 항목만 수집합니다.
- 전체번호 반환·출력을 역할별로 제한하고 마스킹된 조회를 기본값으로 검토합니다.


### 완료 기준


서버 분실·백업 파일 유출 가정에서 업무 데이터를 보호하고, 권한 없는 사용자는 백업·키에 접근하지 못해야 합니다. 승인된 복구 담당자는 별도 키로 실제 복구할 수 있어야 합니다. 체크섬은 손상 탐지 수단이며 출처 서명·암호화를 대신하지 않습니다.


## 12. 우선 보완 F03 — 복구·백업 운영

높음 · 자료 백업과 서버 전체 복구의 차이


### 잘된 점과 빠진 범위


전체백업은 SQLite 온라인 백업·무결성 검사, 첨부 복사, 파일별 해시를 포함합니다. 복원 시 경로·중복·심볼릭 링크·크기를 검사하고, 기존 data를 별도 보존한 뒤 교체합니다. 반면 ZIP에는 certificates, lan_settings.json, 프로그램 본체, Windows 인증서 저장소의 CA 개인키·사용자 DPAPI 프로필이 포함되지 않습니다. [E05, E06, E14]


따라서 같은 PC의 업무 자료 복원과, 고장난 PC를 새 Windows PC로 교체한 뒤 같은 로그인·신뢰 환경까지 복구하는 일은 다릅니다. DPAPI 암호문은 다른 Windows 사용자에서 열리지 않을 수 있으며, CA 개인키가 없으면 기존 CA로 서버 인증서를 갱신할 수 없습니다. 비밀번호 초기화·다시 로그인, 새 CA 등록 또는 별도 안전한 CA 복구 절차가 필요합니다.


### 동일 디스크 백업·증가량 문제


자동 백업은 쓰기 전에 시도하며 일반 작업은 최소 300초 간격으로 제한합니다. 하지만 백업 ZIP과 DB를 같은 서버 경로에 쌓고, 백업 파일의 자동 보존 개수·기간 제한은 확인되지 않았습니다. 서버 로그의 회전과 백업 보존 정책은 서로 다릅니다. 자동 백업 실패는 경고를 남기고 일부 업무 저장은 계속 진행합니다. [E01 app.py:329]


용량 경계에도 주의가 필요합니다. 첨부 업로드는 누적 2GB까지 허용하지만 복원 검증은 압축 해제 전체 2GB를 상한으로 둡니다. 첨부가 한도에 가까우면 DB·키·메타데이터를 더한 백업이 복원 한도를 넘을 수 있습니다. 이는 코드 상한 비교로 확인한 잠재 불일치이며 2GB 실파일 복구 시험은 수행하지 않았습니다. 생성·검증·첨부 한도를 일관되게 맞추고 여유를 두어야 합니다. [E03 operations.py:375, E05 backup_manager.py:48]


용량 예: DB 크기를 D, 전체 ZIP을 Z라 하면 8시간 동안 5분마다 쓰기가 있는 경우 약 96×(D+Z)가 하루에 추가될 수 있습니다. 실제 횟수·압축률·중요 작업에 따라 달라지는 산식이며 실측 용량은 아닙니다. 첨부가 늘면 반복 전체 ZIP 비용도 증가합니다.


### 권고와 완료 기준


- 업무일 종료 후 자동 별도 보관, 암호화, 보존·삭제, 실패·여유공간 경보를 운영합니다. 단순히 프로그램 폴더만 복사하지 않습니다.
- 현재 ZIP·DB 백업과 접속 환경 복구 자료를 구분합니다. 인증서 개인키 백업은 클라이언트 배포물과 분리해 제한된 담당자가 보호합니다.
- 새 PC 복구 연습으로 건수·합계·첨부·계정·중복 등록부·수기 정정·하이패스 상태를 대조하고, 접속 인증서 신뢰와 권한까지 확인합니다.
- 목표 손실 허용량(RPO)과 복구 시간(RTO)은 회사가 정하고 실제 시간을 측정합니다. 현재 코드만으로 몇 분 이내 복구를 보장할 수 없습니다.


## 13. 우선 보완 F04 — 가용성·성능·용량

중간~높음 · 단일 서버 운영의 한계


### 확인한 구조


HTTP 작업자는 최대 16개, 대기 슬롯은 32개입니다. 주요 업무 변경은 프로세스 전역 잠금으로 직렬화하고 현재 상태를 읽어 검증·저장합니다. DB는 레코드 테이블을 갖추었지만 storage.read는 여러 업무 목록 전체를 읽으며 write도 전체 목록을 비교합니다. 화면은 기본적으로 2초마다 상태 확인을 합니다. 변경이 없으면 작은 응답을 반환하는 최적화가 있습니다. [E03, E06, E13]

### 운영 영향


서버 창 종료, 사용자 로그오프, 재부팅·절전, 디스크 문제는 접속 중단으로 이어질 수 있습니다. 이번 패키지의 권장 실행 경로는 콘솔 기반이며 중앙 서비스 감시·이중화가 확인되지 않습니다. 많은 이력과 첨부·동시 저장에서는 전체 상태 처리와 백업 때문에 지연·충돌이 늘 수 있습니다. 슬롯 제한은 자원 고갈을 줄이지만 사용 인원 보장 수치는 아닙니다.


### 개선 방향


- 지정 업무 PC 또는 회사 관리 서버에서 운영하고 절전·재시작·보안 업데이트·실행 계정·서버 종료 권한을 관리합니다. Windows 서비스/작업 스케줄러 전환은 별도 검증 후 적용합니다.
- 조회는 서버 페이지 처리·기간/지점 인덱스·필요 필드 API로 옮기고, 업무 단위 DB 변경으로 전체 상태 비교를 줄입니다. 현재 일부 페이지 API가 있어도 화면 전체 상태 동기화가 사라진 것은 아닙니다.
- 실제 예상 자료량과 조회+불출+반납+승인+이관+백업 혼합 부하를 측정합니다. 회사가 정한 허용 응답시간·오류율·복구 기준으로 용량을 확정합니다.

### 설계상 좋은 선택을 유지할 부분


원본과 정정본 분리, 잘못된 값의 묵시적 0원 변환 금지, 이관완료와 승인완료 구분, 동일 작업 중복 방지, 타 지점 자료의 서버 차단, 기존 DB를 보존하는 업데이트는 유지해야 합니다. 편의 기능을 추가하면서 이 원칙을 약화시키지 않아야 합니다.


### 기술 부채의 실제 규모


HTML은 3,913줄, app.py 1,158줄, operations.py 569줄입니다. 줄 수만으로 품질을 판단하지는 않지만 HTML·스타일·화면 로직·업무 기능이 한 파일에 집중되어 변경 영향 파악이 어렵습니다. 화면·공통 컴포넌트·API 클라이언트·업무 상태 정의를 점진적으로 분리하고, 신규 기능마다 핵심 업무 회귀 검사를 유지하는 편이 적절합니다.


> 현재 버전을 “완벽한 기업용 완제품”으로 표현하기는 어렵습니다. 반대로 기능이 없거나 검증 기반이 없는 시제품으로 보는 것도 정확하지 않습니다. 현업 기능이 축적된 경량 업무 시스템이며, 기업 운영 통제를 마무리해야 하는 단계입니다.

### 기존 자동 검사가 다루는 중요한 실패 경로


지점·읽기 전용 권한 차단, 승인 위조 방지, DB 손상 보존, 트랜잭션 롤백, 중복·응답 유실 재시도, 최대2,000행 이관, 버전 충돌, 수기 정정 연결, 전체백업·복원, 첨부 권한·공지 삭제 후 접근 차단 등을 포함합니다. 이 결과는 기능 안정성의 긍정 근거입니다.


### 시험 환경 보정 기록


최초 Python 실행은 로컬 요청이 시험 환경의 외부 프록시로 전달되어 다수 403 Domain forbidden이 발생했습니다. 로컬 주소를 프록시 제외한 뒤 전체를 다시 실행한 최종 결과를 위에 기재했습니다. 이 최초 환경 오류를 제품 결함이나 통과로 계산하지 않았습니다. 실패 경로 테스트의 의도된 ERROR 로그도 최종 실패 수와 구별했습니다.


### 미검증을 남겨 두어야 하는 것


회사 Windows·Edge/WebView2·인증서 신뢰·방화벽, 실제 Oracle, 실제 회사 전체 데이터, 다일간 연속 운영, 장비 장애·랜섬웨어·OS 계정 변경, 전문 침투 시험은 통과로 표시하지 않았습니다. Windows CI 매트릭스 정의만으로 회사 PC 실기 검증을 대체하지 않습니다.

### 운영자가 평소 확인할 것


- 매일: 서버 가동·최근 백업·여유 공간·백업 경고·미반납/미정산/미확인 이관을 확인합니다.

- 업데이트 전: 기존 실행 폴더의 자료로 전체백업을 만들고 서버를 정상 중지합니다. 새 프로그램만 교체한 뒤 로그인·한 건 업무·이력·첨부·합계를 확인합니다. DB를 다른 버전으로 임의 덮어쓰지 않습니다.
- 원격 사용: 사설 IP만으로 집에서 접속되지 않습니다. 회사 승인 VPN 등과 서버 가동이 필요하며, 공유기 포트 개방만으로 해결하려 하지 않습니다.


### 최종 결론


V4.1.20은 법인카드·하이패스·유류대카드 관리의 실제 흐름과 자료 추적 장치를 갖추고 있어, 제한된 사내 업무를 지원할 기반은 있습니다. 가장 잘된 점은 자료를 보호하며 정정·중복·충돌을 다루는 설계입니다. 가장 먼저 보완할 점은 비밀번호·백업 보호와 새 PC 복구, 관리자 통제, 운영 감시입니다.


회사의 실기·복구·대사 결과가 없는 상태에서는 전면 도입을 확정할 수 없습니다. 권고는 “통제 조건을 충족한 보조 업무 시범 운영”입니다. 이 조건을 완료하고 실제 업무 결과를 확인한 뒤 정식 운영 범위와 Oracle 통합 범위를 결정하십시오.

| 접속 환경 백업 | TLS·LAN 설정은 ZIP에 없음 | 현재 프로그램 업데이트가 이 파일을 보존하는 것과 백업 포함 여부는 별개 |


### 첨부 증거 파일


증거 묶음에는 최종 Python/Node/브라우저/단기 부하 로그, 합성 관찰 결과와 재현 스크립트, 패키지 해시·보고서 해시를 포함합니다. 회사 DB·비밀번호·개인 Excel·TLS 개인키는 포함하지 않습니다. 테스트 계정명과 암호 문자열은 임시 합성 환경 전용입니다.


### 해석과 책임 범위


우선도 “높음”은 회사 업무의 기밀성·복구·승인 신뢰에 미치는 영향을 기준으로 한 개선 우선순위입니다. CVSS 점수나 침해 발생 증거가 아닙니다. 잠재 위험·구현상의 제약·업무 정책·미검증 범위를 구분했습니다. 결함을 수정한 패키지를 이 보고서에 포함하거나 검토만으로 운영 승인을 확정하지 않았습니다.


다음 단계는 보고서의 도입 체크리스트를 회사 담당자와 확인하고, 우선 보완 범위와 승인 기준을 정하는 것입니다. 기존 기능을 전면 재작성하기보다 자료 보호 원칙을 유지하면서 통제 공백부터 보완하는 접근이 적절합니다.
